# Technology Stack

## 1. Overview

This document describes the current technology stack used by the SENTINEL Case Management Console MVP and the intended direction for later phases.

## 2. Current MVP Stack

| Layer | Technology | Purpose |
| --- | --- | --- |
| Front end | React 18 | Component-based UI for the intelligence console |
| Language | TypeScript 5 | Static typing for domain entities and UI logic |
| Build tool | Vite 5 | Fast local development server and production bundling |
| Rendering | React DOM | Browser rendering for the SPA |
| API server | Express 5 | API for authentication workflow, state, mutations, reports, and audit events |
| ORM | Prisma | Schema management, migrations, seed data, and typed database access |
| Database | PostgreSQL 16 | Transactional persistence for cases, subjects, evidence, reports, sessions, and audit events |
| Graph layout | d3-force | Force-directed relationship graph for case, subject, and evidence links |
| Styling | Custom CSS | Tactical visual design and responsive layout |
| Session cache | browser localStorage | Stores the lightweight API token and operator metadata |
| Package manager | npm | Dependency management and scripts |

## 3. Development Tooling

| Tool | Role |
| --- | --- |
| TypeScript compiler | Type checking during build |
| ESLint | Static linting baseline |
| Vite dev server | Local development and preview |
| tsx | Runs the TypeScript API server in development |
| concurrently | Runs API and Vite together with `npm run dev:full` |
| Docker Compose | Runs PostgreSQL, API, web, and Adminer for local production-style development |
| esbuild | Bundles the Express API for the production runtime image |

## 4. Runtime Model

1. The application is a client-rendered single-page application.
2. Domain state is hydrated from the Express API and held in React state while the UI is open.
3. Mutations are sent to the API, which writes PostgreSQL through Prisma and returns the updated state.
4. Reports are generated by the API as HTML artifacts and previewed in the browser.
5. Browser localStorage stores session metadata only.

## 5. Why This Stack Was Chosen

1. React + TypeScript provides fast UI iteration with typed domain modeling.
2. Vite keeps setup light and is compatible with the empty-workspace bootstrap used here.
3. `d3-force` supports the relationship-graph requirement from the earlier SENTINEL concept.
4. Custom CSS preserves a distinct operational-console UI rather than a generic component-library look.
5. Dockerized PostgreSQL keeps local development close to the intended production persistence model.

## 6. Current Stack Limitations

1. The current PostgreSQL setup needs managed backups, monitoring, and secret handling before real deployment.
2. Demo access-key authentication is not a substitute for enterprise identity and RBAC.
3. HTML report generation is acceptable for a demo but not for controlled document workflows.
4. Custom CSS is flexible but will need stronger component structure as the app grows.
5. The current API still needs stronger module boundaries, tests, and deployment hardening as the system grows.

## 7. Recommended Future Stack Direction

| Layer | Recommended Direction |
| --- | --- |
| Authentication | Enterprise SSO or approved identity provider with RBAC |
| Backend API | Node.js or .NET service layer for case, subject, evidence, and audit domains |
| Database | Managed PostgreSQL or approved relational platform for structured operational records |
| Search | OpenSearch or Elasticsearch-style indexing service |
| Object storage | Secure evidence/document storage with retention and integrity controls |
| Audit | Append-only audit service or tamper-evident event store |
| Analytics | Dedicated services or pipelines for enrichment, correlation, and context extraction |
| Deployment | Segregated dev, test, and production environments |

## 9. Operational Notes

1. The current full-stack MVP can be served locally with `npm run dev:full`.
2. The current production validation command is `npm run build`.
3. Vite proxies `/api` to `http://localhost:4310` during local development.
4. Docker Compose exposes PostgreSQL on localhost port `5433` and Adminer on `18082` for local development.
5. The current Node runtime on this machine successfully built the project with the Vite 5 scaffold used in the repository.
